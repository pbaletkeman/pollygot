2. MainApplication.doWork() rewritten
private static final int PRODUCERS = 3;
private static final int CONSUMERS = 5;

private String doWork() throws InterruptedException {
    TaskIdGenerator generator = new TaskIdGenerator();
    Statistics statistics      = new Statistics();
    TaskTracker tracker        = new TaskTracker();
    QueueManager queue         = new QueueManager(10000);
    Producer producer          = new Producer(queue, generator, statistics);
    Consumer consumer          = new Consumer(queue, tracker, statistics);

    ExecutorService producerPool = Executors.newFixedThreadPool(PRODUCERS, named("producer"));
    ExecutorService consumerPool = Executors.newFixedThreadPool(CONSUMERS, named("consumer"));
    try {
        // --- start the 5 consumers first: they block on an empty queue ---
        List<Future<?>> consumers = IntStream.range(0, CONSUMERS)
            .mapToObj(i -> consumerPool.submit(consumerJob(consumer)))
            .toList();

        // --- 3 producer jobs: 3333 + 3333 + 3334 = 10000 ---
        List<Future<?>> producers = List.of(
            producerPool.submit(producerJob(producer, 3333)),
            producerPool.submit(producerJob(producer, 3333)),
            producerPool.submit(producerJob(producer, 3334)));

        // step 1: producers MUST terminate before pills, or a pill overtakes a task
        producerPool.shutdown();
        if (!producerPool.awaitTermination(30, TimeUnit.SECONDS)) {
            producerPool.shutdownNow();
            throw new IllegalStateException("producer pool hung");
        }
        for (Future<?> f : producers) f.get();   // surfaces a swallowed task exception

        // step 2: one pill per consumer, bypassing Statistics
        for (int i = 0; i < CONSUMERS; i++) {
            queue.submitTask(new Task(Task.SHUTDOWN, "shutdown", LocalDateTime.now()));
        }

        // step 3: wait for all consumers to drain and exit
        consumerPool.shutdown();
        if (!consumerPool.awaitTermination(30, TimeUnit.SECONDS)) {
            consumerPool.shutdownNow();          // interrupts blocked take()
            throw new IllegalStateException("consumer pool hung - missing poison pill?");
        }
        for (Future<?> f : consumers) f.get();

        return statistics.getReport();
    } finally {
        // belt & braces: never leak non-daemon pool threads
        producerPool.shutdownNow();
        consumerPool.shutdownNow();
    }
}
Two small helpers so the checked-exception story stays explicit:
private static Runnable producerJob(Producer p, int n) {
    return () -> {
        try { p.addTasks(n); }
        catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    };
}

private static Runnable consumerJob(Consumer c) {
    return () -> {
        try { c.run(); }
        catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    };
}

private static ThreadFactory named(String prefix) {
    AtomicInteger n = new AtomicInteger();
    return r -> new Thread(r, prefix + "-" + n.incrementAndGet());
}
(Thread names matter — your tests and MainApplication diagnostics identify workers by name, and the default factory gives you pool-1-thread-3 instead.)

4. Poison pills vs. queue close (recommended improvement)
BlockingQueue already has close() — and you already have a passing test proving it drains remaining items, then returns null, while Consumer.run() already exits on null:
public void run() throws InterruptedException {
    Task task = queue.getTask();
    if (task == null) return;              // <- close() path
    if (task.getTaskId() == Task.SHUTDOWN) return;   // <- pill path
    ...
}
So you can add one line to QueueManager:
public void close() { this.queue.close(); }
and replace the pill loop with queue.close();. Why it's better with executors:
- Pills are a per-worker sentinel: count must equal CONSUMERS exactly. With a pool you think in terms of "the pool", not "these 5 particular threads" — one extra submit() and a consumer hangs forever.
- close() is one idempotent operation that releases every blocked take().
- It's also the honest production story: close the source, let workers drain, then awaitTermination — exactly how you'll shut down a real worker pool in week 2.
Keep the pills if you want them as a documented alternative (they also let you demo both mechanisms); the ordering invariant — never signal shutdown while producers can still add work — is identical in both cases.
5. Pitfalls to avoid (good interview material)
1. shutdown() ≠ threads stopped. It only rejects new tasks; parked take() threads never wake up. You always need awaitTermination(timeout) → shutdownNow() (which interrupts).
2. awaitTermination returns boolean. Ignoring the return value recreates exactly the unbounded hang we just fixed — pair it with JUnit @Timeout as an outer guard.
3. submit() swallows exceptions. A thrown exception is stored in the Future and rethrown only on get(). Use execute() if you want it on the thread's uncaught handler, or always get().
4. Don't submit 10,000 jobs to the pool. newFixedThreadPool uses an unbounded internal queue; submitting per-task jobs would move the buffering off your BlockingQueue and destroy the backpressure story. Submit 8 long-running jobs; the queue stays the single choke point.
5. Don't use newCachedThreadPool() here — unbounded thread growth contradicts "3 producers / 5 consumers" and is a classic interview trap (cached pool + no bounds = OOM under load).
6. InterruptedException handling — restore the flag (Thread.currentThread().interrupt()), never swallow it, or shutdownNow() becomes a no-op for subsequent checks.
7. Reusing one pool across runs is fine for producers, but consumers that already exited (return on pill/null) won't come back — for the 5-run test, create the consumer pool per run, or rely on close() + a fresh QueueManager.
